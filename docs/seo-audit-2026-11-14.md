# LazyDM landing-page SEO audit

Audit date: 2026-11-14  
Scope: `https://lazydm.com/` and the static source in `site/`  
Primary conversion: follow the pre-1.0 project on GitHub  
Provisional primary query: **campaign manager for Dungeon Masters**  
Secondary query: **encounter tracker for Dungeon Masters**

The query targets are provisional because Search Console and keyword-volume data were not available. They follow the
product's category, audience and current title rather than an invented search-volume estimate.

## Executive summary

The page has a healthy technical base for a one-page, pre-release product site. The canonical URL returns `200`; HTTP
and `www` redirect to it; `robots.txt` and `sitemap.xml` are reachable; the page has a canonical, unique title and meta
description, one H1, descriptive image alternatives, responsive WebP screenshots and relevant structured data.

The original hero left the desk-to-table workflow to the lede and title tag. The hero now keeps `LazyDM.` as the product
H1 and places `Prep the campaign. Run at the table.` directly beneath it as the promise; the next paragraph immediately
names the category and audience. The remaining constraints are external or product-stage issues: no Search Console
evidence, no public release to convert visitors to, no earned proof yet, and no supporting content for broader
non-branded searches.

## Findings

### 1. The old hero did not state the desk-to-table promise

- **Impact:** High
- **Evidence:** The product name stood alone above the lede. The category and audience appeared in the title and opening
  paragraph, but the hero did not state the product's desk-to-table promise.
- **Fix shipped:** The product name remains the H1 and the adjacent tagline now states the core workflow: `Prep the
  campaign. Run at the table.` The first paragraph immediately supplies the category and audience: desktop campaign
  manager and encounter tracker for Dungeon Masters.
- **Status:** Fixed

### 2. The hero CTA described the destination, not the visitor's next step

- **Impact:** Medium
- **Evidence:** `View LazyDM on GitHub` is accurate but passive. The page's actual pre-release goal is to let a DM follow
  development until downloads exist.
- **Fix shipped:** Changed both primary CTAs to `Follow development on GitHub`; availability remains explicit beside
  the CTA and in the status callout.
- **Status:** Fixed

### 3. Several sections led with features instead of the table workflow

- **Impact:** Medium
- **Evidence:** The page had strong product detail, but longer passages made the benefit harder to scan, especially in
  the Tracker and split-screen sections.
- **Fix shipped:** Tightened the copy around concrete actions: reuse prepared stat blocks, keep scenes beside maps,
  switch the map beside the encounter when play begins, and retain Markdown ownership.
- **Status:** Fixed

### 4. Social metadata was incomplete on X/Twitter

- **Impact:** Low for rankings; medium for shared-link presentation
- **Evidence:** The page set a Twitter card and image but relied on Open Graph fallbacks for the title and description
  and had no Twitter image alternative.
- **Fix shipped:** Added explicit Twitter title, description and image alternative.
- **Status:** Fixed

### 5. Non-branded organic reach depends on one page

- **Impact:** High, long term
- **Evidence:** The sitemap correctly contains only the homepage. The page covers product intent well, but one URL has
  limited ability to satisfy narrower searches such as Obsidian-compatible campaign management, D&D 5e encounter
  tracking, Pathfinder 2e encounter tracking, Markdown campaign notes and interactive RPG maps.
- **Recommendation:** After the product is downloadable, create a small set of genuinely useful feature/use-case pages.
  Give each page one distinct intent and link it from the relevant homepage section. Do not make thin keyword variants.
- **Status:** Recommended after release scope is settled

### 6. The page has no external proof yet

- **Impact:** Medium for conversion and trust; indirect SEO impact
- **Evidence:** There are no testimonials, usage figures, reviews, public releases or benchmarks. The page correctly
  avoids inventing them.
- **Recommendation:** Once evidence exists, place one specific proof point near the hero or first CTA and a relevant
  quote or release signal near the final CTA. A named quote, release count or public changelog is more useful than an
  unsupported `trusted by` claim.
- **Status:** Blocked on real evidence

### 7. Core Web Vitals require field or rendered measurement

- **Impact:** Medium
- **Evidence:** The implementation is lean (static HTML/CSS/JS, local fonts, no third-party scripts), screenshots have
  fixed dimensions, responsive sources and lazy loading. However, source inspection does not measure LCP, INP or CLS.
  Both light and dark screenshots are present in the DOM, so a browser network trace should confirm whether it downloads
  both variants as each section approaches the viewport.
- **Recommendation:** Check mobile and desktop PageSpeed Insights after deployment, then use Search Console field data
  once available. Investigate only measured regressions; start with dual-theme image requests if transfer size is high.
- **Status:** Measurement required

### 8. Structured data is present and appropriately conservative

- **Impact:** Low to medium
- **Evidence:** Source contains `WebSite` and `SoftwareApplication` JSON-LD with name, category, operating systems,
  description, canonical URL, image and GitHub identity. It does not invent ratings, offers or a downloadable release.
- **Recommendation:** Validate the deployed page with Google's Rich Results Test after each material schema change.
  Add offers, version and download URL only when those facts exist.
- **Status:** Healthy; rendered validation still required

## Prioritized next actions

1. Deploy this refactor and submit or re-request the homepage in Google Search Console.
2. Record impressions, clicks, CTR and average position for the provisional query targets for at least four weeks.
3. Run PageSpeed Insights on the deployed URL and retain the report as a baseline.
4. Validate the deployed JSON-LD with the Rich Results Test.
5. When downloads exist, change the primary CTA from following development to the real download action and add valid
   release details to the software schema.
6. Build supporting pages only from demonstrated search demand and real product depth.

## Copy diagnosis

This was a **Situation B** edit: the original already had a distinct voice, an arguable desk-to-table position and
product-native terms. The refactor preserves that argument and vocabulary, removes repetition, makes benefits easier to
scan and keeps every availability and product claim within the evidence in `PRODUCT.md`.
